Customer Lifetime Value Prediction

2Initial Setup · RFM Computation Query

RFM Score Calculation

rfm_scoring.sql
WITH rfm_raw AS ( SELECT customer_id, CURRENT_DATE - MAX(order_date)::date AS recency_days, COUNT(order_id) AS frequency, SUM(order_value) AS monetary FROM orders GROUP BY customer_id ), rfm_scored AS ( SELECT *, NTILE(5) OVER (ORDER BY recency_days ASC) AS r_score, NTILE(5) OVER (ORDER BY frequency DESC) AS f_score, NTILE(5) OVER (ORDER BY monetary DESC) AS m_score FROM rfm_raw ) SELECT customer_id, recency_days, frequency, monetary, r_score, f_score, m_score, (r_score + f_score + m_score)::numeric / 3 AS rfm_avg_score FROM rfm_scored ORDER BY rfm_avg_score DESC;
3Insights & Analysis

CLV & RFM Segmentation Findings

RFM segmentation surfaced a "Sleeping Champions" cluster — customers with historically high monetary scores but low recent recency scores — representing a significant win-back revenue opportunity.

  • "Champions" segment (RFM score ≥ 4.5) represented 8% of the customer base but contributed 54% of total LTV.
  • 147 "Sleeping Champions" identified with average historical spend of $3,200/year — prioritised for a win-back campaign.

Inventory Optimization Queries

EnginePostgreSQL 15
ModelEOQ · Reorder Point · Safety Stock
EOQ ModelingLogistics SQLSupply Chain
1Introduction & Background

Project Overview

This project implements the Economic Order Quantity (EOQ) model, reorder point thresholds, and safety stock calculations directly in SQL — eliminating the need for manual spreadsheet inventory reviews. The queries operate against live inventory transaction tables and produce a daily "action required" list for the procurement team.

2Initial Setup · EOQ & Reorder Query

EOQ Calculation & Reorder Point Logic

eoq_reorder.sql
WITH demand_stats AS ( SELECT sku_id, AVG(daily_units_sold) AS avg_daily_demand, STDDEV(daily_units_sold) AS demand_stddev, AVG(lead_time_days) AS avg_lead_time FROM inventory_transactions GROUP BY sku_id ), eoq_calc AS ( SELECT d.*, p.unit_cost, p.annual_holding_cost_pct, p.order_cost, -- EOQ formula: √(2DS/H) SQRT( (2 * (d.avg_daily_demand * 365) * p.order_cost) / (p.unit_cost * p.annual_holding_cost_pct) ) AS eoq, -- Safety stock: Z(1.65) × σ × √(lead_time) ROUND(1.65 * d.demand_stddev * SQRT(d.avg_lead_time)) AS safety_stock FROM demand_stats d JOIN product_params p ON d.sku_id = p.sku_id ) SELECT sku_id, ROUND(eoq) AS optimal_order_qty, safety_stock, ROUND(avg_daily_demand * avg_lead_time + safety_stock) AS reorder_point FROM eoq_calc ORDER BY reorder_point DESC;
3Insights & Analysis

Inventory Optimization Findings

Implementing data-driven EOQ calculations exposed that the business was significantly over-ordering slow-moving SKUs while under-ordering fast-moving ones — a classic inventory imbalance caused by experience-based ordering rather than demand-signal-driven procurement.

  • 12 SKUs were identified as systematically over-ordered by an average of 340%, tying up ~$180K in excess working capital.
  • 7 high-velocity SKUs had reorder points set below safety stock — creating stockout risk during lead time variance events.
  • Implementing EOQ-based ordering was projected to reduce total inventory holding costs by 22% annually.
  • Daily "action required" view reduced procurement team review time from 2 hours to 12 minutes per day.

Automated Data Cleaning Pipeline

LanguagePython 3.11
LibrariesPandas · NumPy · Logging
PandasNumPyPipelines
1Introduction & Background

Project Overview

Recurring report exports from legacy ERP systems arrived with unpredictable schema variations, renamed columns, and inconsistent data types. This reusable Pandas/NumPy pipeline applies configurable cleaning transformations, handles schema drift through column-name aliasing, flags statistical outliers, and produces structured execution logs for auditability.

The pipeline is designed as a Python class that can be instantiated with a YAML configuration file, making it reusable across datasets without code changes.

2Initial Setup · Pipeline Class Definition

Core Pipeline Setup Code

cleaning_pipeline.py
import pandas as pd import numpy as np import logging from pathlib import Path # Configure structured logging for pipeline audit trail logging.basicConfig( level=logging.INFO, format="%(asctime)s | %(levelname)s | %(message)s" ) class DataCleaningPipeline: """Reusable data cleaning pipeline with schema drift handling.""" def __init__(self, config: dict): self.config = config self.log = logging.getLogger(self.__class__.__name__) self.report = {} def load(self, filepath: str) -> pd.DataFrame: df = pd.read_csv(filepath, low_memory=False) self.log.info(f"Loaded {len(df):,} rows from {Path(filepath).name}") return df def standardise_columns(self, df: pd.DataFrame) -> pd.DataFrame: # Alias map handles schema drift across export versions alias = self.config.get("column_aliases", {}) df = df.rename(columns=alias) df.columns = df.columns.str.lower().str.replace(" ", "_") return df def flag_outliers(self, df: pd.DataFrame, col: str) -> pd.DataFrame: q1, q3 = df[col].quantile([0.25, 0.75]) iqr = q3 - q1 df[f"{col}_outlier"] = ~df[col].between(q1 - 1.5*iqr, q3 + 1.5*iqr) return df
3Insights & Analysis

Pipeline Performance & Quality Findings

Automating the cleaning process via a configurable pipeline eliminated approximately 4 hours of weekly manual analyst work while simultaneously improving data quality consistency — the manual process had an estimated 12% error rate in outlier identification due to inconsistent threshold application.

  • Pipeline processes a standard 100K-row export in under 8 seconds versus ~45 minutes manually.
  • Schema drift handling successfully processed 7 different column naming conventions from 3 ERP export formats without code changes.
  • IQR-based outlier flagging identified 2.1% of records as statistical outliers — 40% higher than the manual process was capturing.
  • Structured logging enabled full auditability with per-column transformation records for compliance requirements.

import pandas as pd import seaborn as sns import matplotlib.pyplot as plt from scipy import stats # Load dataset df = pd.read_csv("sales_data.csv") # Central tendency & dispersion summary summary = df[["revenue", "units_sold", "discount_pct"]].agg([ "mean", "median", "std", "skew", "kurt" ]) # Normality test (Shapiro-Wilk on sample) sample = df["revenue"].sample(5000, random_state=42) stat, p_val = stats.shapiro(sample) print(f"Shapiro-Wilk: stat={stat:.4f}, p={p_val:.4e}") # Distribution plot fig, axes = plt.subplots(1, 2, figsize=(14, 5)) sns.histplot(df["revenue"], kde=True, ax=axes[0]) stats.probplot(df["revenue"], plot=axes[1]) plt.tight_layout() plt.savefig("distribution_analysis.png", dpi=150)
3Insights & Analysis

Statistical Findings

The distribution analysis revealed that revenue was positively skewed (right-tailed) with significant kurtosis, confirming that a small number of very large orders disproportionately drove the mean above the median — an important insight for choosing median-based targets rather than mean-based.

  • Revenue distribution had a skewness of +2.34 — confirming a long right tail driven by enterprise order outliers.
  • Shapiro-Wilk test confirmed non-normality (p < 0.001), requiring non-parametric tests for subsequent hypothesis testing.
  • Discount percentage and units sold showed negative correlation (r = -0.41) — higher discounts correlated with fewer total units in some categories.
  • Inter-quartile range analysis isolated 4.8% of orders as high-value outliers that accounted for 38% of total revenue.

This project implements the Apriori algorithm via Mlxtend to discover association rules from e-commerce transaction data. The goal is to identify product pairs and bundles that are frequently purchased together — generating actionable cross-sell recommendations and bundle pricing strategies for the merchandising team.

2Initial Setup · Transaction Matrix & Apriori Config

Basket Encoding & Association Rule Mining

market_basket.py
import pandas as pd from mlxtend.frequent_patterns import apriori, association_rules from mlxtend.preprocessing import TransactionEncoder df = pd.read_csv("transactions.csv") # Build basket: one row per order, one column per product (0/1) basket = (df.groupby(["order_id", "product_name"])["quantity"] .sum().unstack(fill_value=0).reset_index()) basket = basket.drop(columns=["order_id"]).applymap( lambda x: 1 if x > 0 else 0 ) # Mine frequent itemsets frequent_items = apriori( basket, min_support=0.02, # item pair appears in ≥2% of baskets use_colnames=True, max_len=3 # max bundle size = 3 products ) # Generate association rules filtered by lift rules = association_rules( frequent_items, metric="lift", min_threshold=1.5 ).sort_values("lift", ascending=False)
3Insights & Analysis

Association Rule Findings

The Apriori analysis on 240K transactions mined 847 frequent itemsets and condensed them to 34 high-confidence association rules. The strongest rules revealed intuitive but previously unquantified bundle opportunities — now presented to the merchandising team with lift, confidence, and revenue impact estimates.

  • Top rule: {Laptop Stand} → {USB-C Hub} had a lift of 4.2 and confidence of 72% — customers buying a stand were 4× more likely to also buy a hub.
  • A 3-product bundle rule was discovered: {Coffee Grinder, Scales} → {Pour-over Kit} with lift 3.8 and support 3.4%.
  • Implementing the top 5 cross-sell rules in checkout recommendations projected a $48K incremental monthly revenue uplift.
  • 6 high-support rules identified products that should be physically co-located in warehouse zones to reduce pick time.

This project implements the Markowitz Efficient Frontier using historical equity return data to identify the optimal portfolio allocation that maximizes the Sharpe Ratio. A Monte Carlo simulation generates 10,000 random portfolio weight combinations, plotting the risk-return space and identifying the minimum variance and maximum Sharpe portfolios.

Markowitz Frontier & Monte Carlo Simulation

portfolio_optimization.py
import numpy as np import pandas as pd import matplotlib.pyplot as plt # Historical returns (daily) for portfolio assets returns = pd.read_csv("asset_returns.csv", index_col=0, parse_dates=True) mean_returns = returns.mean() * 252 # annualised cov_matrix = returns.cov() * 252 n_assets = len(returns.columns) # Monte Carlo: 10,000 random portfolios n_portfolios = 10_000 results = np.zeros((3, n_portfolios)) for i in range(n_portfolios): weights = np.random.dirichlet(np.ones(n_assets)) p_return = np.dot(weights, mean_returns) p_vol = np.sqrt(weights @ cov_matrix @ weights) results[0, i] = p_return results[1, i] = p_vol results[2, i] = (p_return - 0.05) / p_vol # Sharpe (rf=5%) # Identify Sharpe-maximizing portfolio max_sharpe_idx = results[2].argmax() max_sharpe_return = results[0, max_sharpe_idx] max_sharpe_vol = results[1, max_sharpe_idx] print(f"Max Sharpe Portfolio — Return: {max_sharpe_return:.1%}, Vol: {max_sharpe_vol:.1%}")

The efficient frontier simulation revealed that the current portfolio's Sharpe Ratio of 0.82 was significantly below the optimal portfolio's ratio of 1.41 — achieved primarily by reducing allocation to two high-volatility assets and rebalancing toward a mid-cap value tilt.
